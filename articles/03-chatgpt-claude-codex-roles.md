## 導入

この記事は、ChatGPT・Claude Code・Codex・Notionを組み合わせた「AI駆動開発」というテーマで書いている記事の1本です。実際に運用している[ポートフォリオサイト](https://portfolio.luckrf.blue/)の改修にこの開発フローを適用しながら、実践の中で見えてきたことをもとに書いています。

現在は、ChatGPTを要求整理・壁打ち、Codexをテックリード、Claude Codeを実装担当として使い分けています。

結論から言うと、この分担は「それぞれのAIにしかできない作業」を割り当てたものではありません。要求整理、チケット作成、実装、レビューの文脈を分け、各工程の成果物を次の担当へ受け渡せるようにするための分担です。

役割の一覧だけでは伝わりにくいため、実際に完了したチケット「PO-90：制作実績にポートフォリオサイト自体を追加する」を例に、どのように受け渡したかを紹介します。

## 実例：ポートフォリオサイト自体を制作実績に追加する

PO-90は、ChatGPTとの会話から始まりました。

ポートフォリオサイトを改修していく中で、「このサイトの改修自体も、自分の開発実績として載せられるのではないか」と考えました。単に制作物として掲載するだけでなく、Notionによるチケット管理と、Claude Code・Codexを組み合わせた開発体制についても記載したい、というのが最初の要望でした。

この要望が、実装とレビューを経て完了するまでの流れは次のとおりです。

![実際の受け渡しの流れ](/images/chatgpt-claude-codex-roles-handoff-flow.webp)

### 1. ChatGPTと要求を整理する

まずChatGPTと、何を制作実績として伝えたいのかを整理しました。

- ポートフォリオサイト自体を制作実績に追加する
- 完成した画面だけでなく、継続的に改修していることも伝える
- Notionのチケット管理とGitHubのPR運用を紹介する
- ChatGPT・Codex・Claude Codeと自分の役割分担を記載する
- AIに丸投げしているのではなく、自分が最終判断していることを明確にする

この段階では、まだ実装方法や完了条件までは決めていません。「閲覧者に何を理解してほしいか」をChatGPTとの壁打ちで言語化しました。

要求がまとまった後は、そのままClaude Codeへ実装を頼むのではなく、Codexへチケット作成を依頼するための文章もChatGPTに作ってもらいました。ChatGPTの成果物はコードではなく、次の担当へ要求を誤解なく渡すための依頼文です。

### 2. CodexがNotionのチケットへ落とし込む

ChatGPTが整理した依頼文をCodexへ渡し、NotionにPO-90を作成してもらいました。

作成されたチケットには、次の内容がまとめられています。

- 背景と解決したい課題
- 掲載する情報と表示仕様
- MVPと対象外の範囲
- テスト観点と受け入れ条件
- 実装時の注意点
- 自分・各AI・Notion・GitHubの役割

例えば、非公開リポジトリのGitHub URLは表示しないこと、管理画面から継続更新できること、初期データ投入を再実行しても重複しないことまで完了条件に含めました。

ここでCodexに任せたのは、要求をそのまま書き写すことではありません。要求を実装可能な単位へ構造化し、後から「完了したか」を判定できる状態にすることです。このチケットが、Claude Codeの実装とCodexのレビューで共通して参照する正本になりました。

### 3. Claude Codeがチケットをもとに実装する

次に、Claude CodeへPO-90の対応を依頼しました。Claude CodeはNotionのチケットを確認し、既存の制作実績機能を利用してポートフォリオサイトを登録する処理、表示順の調整、重複登録を防ぐ処理、関連テストを実装し、Pull Requestを作成しました。

この段階では、Claude Codeへ最初の会話から説明し直していません。背景・仕様・対象外・完了条件がNotionに残っているため、「PO-90を対応してください」という単位で実装を渡せます。

### 4. CodexがPRをレビューする

実装後、CodexへPRレビューを依頼しました。最初のレビューでは、次の3点がBlockingとして指摘されました。

1. 既存データに非公開GitHub URLが残っている場合、再実行しても削除されない
2. 注目プロジェクトと通常一覧が、指定した表示順へ必ず収束するとは限らない
3. 複数のSeederを実行する順番によって、古い表示構成へ戻る

Claude Codeが3点を修正し、テストを追加した後、Codexへ再レビューを依頼しました。すると今度は、「同じ順位のデータがある場合」「別の高順位データが存在する場合」という境界条件が残っていることを指摘されました。

Claude Codeが再度ロジックとテストを修正し、最終レビューではBlocking 0件になりました。最終的には、対象機能のテストだけでなく既存テストを含む264件が成功した状態まで確認しています。

一度のレビューで終わらせず、

```text
Codexがレビュー
    ↓
Claude Codeが修正
    ↓
Codexが差分を再レビュー
```

を繰り返したことで、正常系の表示だけでなく、再実行やデータ順序の境界条件まで確認できました。

### 5. 自分が最終判断する

AIを役割分担しても、仕様と公開の責任までAIへ移るわけではありません。

PO-90では、何を実績として見せるか、どの情報を公開するか、ポートフォリオサイトをどの位置に表示するかを自分が決めました。Codexのレビューが完了した後も、レビュー結果と実際の表示を確認し、最終的にマージ・本番反映するかを判断するのは自分です。

## PO-90における役割分担

この実例で各担当が受け取り、次へ渡したものをまとめると、次のようになります。

| 担当 | 受け取ったもの | 次へ渡したもの |
|---|---|---|
| ChatGPT | 「サイト改修自体を実績として載せたい」というアイデア | 整理された要求とCodexへの依頼文 |
| Codex | ChatGPTが整理した依頼文 | 実装可能なNotionチケット、PRレビュー結果 |
| Claude Code | Notionチケット、Codexの指摘 | 実装、テスト、PR、レビュー対応 |
| 自分 | 各AIの提案と実装・レビュー結果 | 仕様の最終決定、マージ、本番反映 |

Notionは要求・仕様・完了条件・レビュー履歴の正本、GitHubはコード・PR・CI結果の正本として使っています。

## なぜ1つのAIで完結させないのか

この分担で重要なのは、どのAIが一番優れているかではありません。

要求を整理したAIとは別の文脈で実装可能性を確認し、実装したAIとは別のAIがレビューする。そうすることで、直前の会話や自分で作った実装をそのまま正しい前提にせず、工程ごとに視点を切り替えられます。

また、担当が変わるたびに、依頼文、Notionチケット、PR、レビュー結果という成果物が残ります。途中の会話をすべて覚えていなくても、正本を読めば次の担当が作業を再開できる点も、この運用の大きな利点です。

この役割分担は絵に描いた餅ではなく、実際にポートフォリオサイトの「注目プロジェクト」欄にも「開発体制：AI協働開発」として掲載しています。

## おわりに

PO-90を振り返ると、ChatGPTは曖昧なアイデアを要求と依頼文にし、Codexは要求を判定可能なチケットへ構造化してレビューし、Claude Codeはチケットと指摘をもとに実装・修正しました。そして、自分が仕様と公開の最終判断をしました。

AIを複数使うこと自体が目的ではありません。工程ごとの役割と受け渡す成果物を決め、AIの出力を別の工程で検証できるようにすることが、この分担の狙いです。
